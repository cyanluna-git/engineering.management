# Phase 3: Remaining Hardcoded English Strings → i18n

## Overview

Phase 3 of the i18n integration replaced **110+ hardcoded English strings** across 8 frontend component/page files with `t()` translation calls. This phase targeted all remaining user-facing strings in ProjectHierarchyEditor, IOManagementTab, ResourceAllocationGrid, ResourcePivotTable, WorklogDrilldownModal, WorklogHeatmap, MilestoneTimeline, and ProjectDetailPage. New locale keys were added to 6 JSON files (EN/KO) across 3 namespaces.

## Context

After Phase 2 (core i18n setup) and Phase 2.5 (error handling i18n), a scan revealed ~150 hardcoded English strings scattered across 6+ components. These included table headers, loading messages, status labels, modal titles, button labels, form placeholders, and UI text that would appear untranslated for Korean users.

### 3. Pattern: Cross-Namespace References

Shared UI strings use cross-namespace `t()` calls to avoid duplication:
```typescript
// From projects namespace, reference common namespace
t('common:buttons.save')    // "Save" / "저장"
t('common:form.name')       // "Name" / "이름"
t('common:status.loading')  // "Loading..." / "로딩 중..."
```

### 4. Pattern: Display-Time Translation for Group Keys

For strings used as both object keys and display text (e.g., "Unassigned" in ResourcePivotTable):
```typescript
// Keep English key for grouping logic
const dept = row.department_name || 'Unassigned';

// Translate only at render time
<span>{deptName === 'Unassigned' ? t('pivot.unassigned') : deptName}</span>
```
